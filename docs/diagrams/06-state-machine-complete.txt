              FORGECTL — Complete State Machine (All 27 States)

  (The implementation phase has two variants: implementing and ui_implementing,
   selected per plan by its kind field — code or ui.)
  State file: .forgectl/state/forgectl-state.json (JSON-backed, atomic writes)

  GENERATE PLANNING QUEUE PHASE
  ═══════════════════════════════════════════════════════════════════════════

  ORIENT ──────► REFINE ──────► PHASE_SHIFT ──[ readiness gate ]──► planning ORIENT
  (generates                    (generate_planning_queue → planning)      │
   plan-queue.json)                                                  BLOCKED: stay
                                                                     in generate_
                                                                     planning_queue

  Notes:
  - ORIENT: auto-generates <state_dir>/plan-queue.json from completed specs
  - REFINE: architect reviews, reorders, edits the file; validates on advance
  - PHASE_SHIFT: consumes plan queue, transitions to planning ORIENT
  - Can be skipped entirely: forgectl advance --from <file> at specifying PHASE_SHIFT
  - PLANNING READINESS GATE: both routes into planning are cold-start entries and
    are gated. Every domain in the incoming plan queue must have an empty
    <domain>/<workspace_dir>/ or the shift is refused, names the dirty domains,
    and mutates nothing. Same check runs at init --phase planning and on demand
    via forgectl preflight. Intra-session domain-boundary re-entries into
    planning ORIENT (planning→planning, implementing/ui_implementing→planning)
    are NOT gated — see 00-full-lifecycle.

                      planning)                                            implementation,

                      (next domain)                                        next plan's kind
                                                                           (implementing or

  Note: a plan with kind: ui enters UI_IMPLEMENTING below instead of IMPLEMENTING.
        Both share this DONE → PHASE_SHIFT exit behaviour.

  Note: COMMIT is reachable ONLY when enable_commits: false. When commits are
        enabled the batch-terminal commit happens inline on the terminal EVALUATE
        advance (message synthesized from the batch's item descriptions) and the
        scaffold lands directly on ORIENT or DONE — COMMIT never appears in the
        transition path, and no --message is ever required to reach it.

  Note: under eval_mode: direct the evaluator corrects the batch files itself, so
        IMPLEMENT runs exactly once per batch and every non-terminal verdict
        re-enters EVALUATE. That self-loop carries the round increment the
        IMPLEMENT→EVALUATE transition would otherwise have applied, so a
        repeatedly-failing batch still climbs to max_rounds and force-accepts.


  UI_IMPLEMENTING PHASE        (entered when the plan's kind is "ui")
  ═══════════════════════════════════════════════════════════════════════════

  Reuses the implementing spine (ORIENT, IMPLEMENT, code EVALUATE, and the same
  batch-terminal commit branch) and inserts a QA loop then an e2e loop between
  EVALUATE and that boundary. Three loops, three independent round budgets
  (eval / qa / e2e), each with its own force-accept at max_rounds.

  ORIENT ──► IMPLEMENT ──► IMPLEMENT ──► EVALUATE          ◄── LOOP 1: code
    ▲         (item 1)      (item N)        │
    │      (each item auto-commits     ┌─────┴───────┐
    │       every round when           │             │
    │       enable_commits: true)  PASS>=min    FAIL<max / PASS<min
    │                              or FAIL>=max      │
    │                                  │      report / conversational:
    │                                  │        IMPLEMENT (round 2+) ──► EVALUATE
    │                                  │      direct:
    │                                  │        EVALUATE ──► EVALUATE (self-loop —
    │                                  │        no re-implement. QA and e2e keep
    │                                  │        UI_REFINE and E2E_REMEDIATE in
    │                                  ▼        every eval_mode)
    │                            QA_TEST ◄───────────┐    ◄── LOOP 2: qa
    │                                │               │        (Playwright MCP)
    │                         ┌──────┴──────┐        │
    │                   PASS>=min      FAIL<max / PASS<min
    │                   or FAIL>=max         │        │
    │                         │              ▼        │
    │                         │          UI_REFINE ───┘
    │                         ▼          (iterate placement/controls)
    │                     E2E_AUTHOR                       (bridge: author tests)
    │                         │
    │                         ▼
    │                     E2E_VERIFY ◄──────────┐         ◄── LOOP 3: e2e
    │                         │                  │            (Playwright runner)
    │                  ┌──────┴──────┐           │
    │            PASS>=min      FAIL<max / PASS<min
    │            or FAIL>=max         │           │
    │                  │              ▼           │
    │                  │          E2E_REMEDIATE ──┘
    │                  ▼          (fix tests or UI, re-run)
    │                  │
    │            BATCH TERMINAL — item status decided HERE: passed if all
    │            three loops passed, failed if any force-accepted
    │                  │
    │            true:  inline auto-commit as part of the terminal
    │                   E2E_VERIFY advance; COMMIT is SKIPPED entirely
    │            false: COMMIT — a state, but no git operation
    │                  │
    │           ┌──────┴──────┐
    └─ more ────┘             │ all done
       batches               ▼
                           DONE ──► PHASE_SHIFT (same routing as IMPLEMENTING:
                                    ui_implementing → planning, or domain
                                    boundary re-routed by next plan's kind)

  Step list: QA_TEST always writes qa/batch-N-steps.json (the contract feeding
             E2E_AUTHOR); the QA loop never exits toward E2E_AUTHOR without it.
