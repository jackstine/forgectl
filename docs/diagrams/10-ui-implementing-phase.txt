================================================================================
           PHASE 4 (UI VARIANT): UI_IMPLEMENTING — State Machine
================================================================================

  Role: Senior Software Engineer (UI)
  Input: plan.json (with passes/rounds fields added by PHASE_SHIFT)
         Selected when the plan's kind is "ui" (see phase-transitions).
  Output: Production UI code + QA reports + authored e2e tests + eval reports
  Evaluators (three sub-agents, three prompts):
    - impl-eval.md     code correctness          (shared with implementing)
    - ui-qa-eval.md    placement / controls      (drives the Playwright MCP)
    - ui-e2e-eval.md   end-to-end verification   (Playwright test runner)

  The ui_implementing phase reuses the implementing phase's spine — layers,
  dependency-ordered batches, one-item-at-a-time IMPLEMENT (per-item auto-commit
  every round when enable_commits: true), the code EVALUATE loop (including its
  eval_mode: "direct" retry, which loops EVALUATE→EVALUATE without re-implementing),
  and the batch-terminal commit boundary — and inserts TWO additional verification
  loops between code EVALUATE and that boundary: a QA placement loop and an
  end-to-end (e2e) loop. Each batch passes three sequential gates before it can
  commit. The batch-terminal commit is COMMIT when enable_commits: false, or an
  inline auto-commit at the terminal E2E_VERIFY transition when enable_commits: true
  (COMMIT is skipped in that case — see LOOP 3 below).

  ═══════════════════════════════════════════════════════════════════════════
  THREE SEQUENTIAL GATES PER BATCH
  ═══════════════════════════════════════════════════════════════════════════

  Every batch passes all three loops, in order, before the batch-terminal
  commit boundary — none skipped:

    IMPLEMENT(s) ─► [ CODE EVAL ] ─► [ QA ] ─► [ E2E ] ─► COMMIT or
                     impl-eval        ui-qa     ui-e2e     inline auto-commit
                     report           Playwright Playwright (enable_commits:
                     verdict          MCP        test runner true skips COMMIT)

  A loop "terminates" when it reaches PASS with rounds >= its min_rounds, or
  force-accepts at its max_rounds. Each loop carries its own round budget and
  its own force-accept boundary, so they are tuned independently.

  Per-loop round counters (reset to 0 at batch selection in ORIENT):
    eval_round   code EVALUATE  loop
    qa_round     QA_TEST ⟲ UI_REFINE loop
    e2e_round    E2E_VERIFY ⟲ E2E_REMEDIATE loop


  ═══════════════════════════════════════════════════════════════════════════
  TWO ACTORS, THREE COMMANDS
  ═══════════════════════════════════════════════════════════════════════════

  ENGINEER (primary agent)          SUB-AGENT (evaluator — code | qa | e2e)
    forgectl advance                  forgectl eval     (context IN)
    forgectl status                   forgectl handoff  (artifacts BACK)

  eval and handoff are valid ONLY in the three evaluator states:
  EVALUATE, QA_TEST, E2E_VERIFY.

  handoff registers the files the sub-agent produced (it verifies each exists),
  surfaces them on a Review: line for the engineer, and carries NO verdict — the
  engineer still records the verdict with advance --verdict. It coexists with
  --eval-report; a divergent --eval-report path warns but does not block.


  ═══════════════════════════════════════════════════════════════════════════
  ITEM STATE PROGRESSION  (in plan.json)
  ═══════════════════════════════════════════════════════════════════════════

  pending ──► done ──► passed   (all three loops PASSed within their budgets)
                 └──► failed   (any loop force-accepted at its max_rounds)

  Terminal status is decided ONLY at the batch-terminal commit boundary (COMMIT
  when enable_commits: false; the inline auto-commit at the terminal E2E_VERIFY
  transition when enable_commits: true), after all three loops have terminated.
  While the batch moves through code / qa / e2e, items stay "done".

  The plan.json items[].rounds field holds eval_round + qa_round + e2e_round
  (a compatibility value matching the implementing-phase shape); the per-loop
  breakdown lives in batch history, not in that single field.

  ARTIFACT LOCATIONS
  ═══════════════════════════════════════════════════════════════════════════

  <domain>/.forgectl_workspace/ui_plan/
  ├── plan.json                              the UI plan (mutated: passes/rounds)
  ├── qa/
  │   ├── batch-N-steps.json                 QA step list (latest round wins)

  │   └── batch-N-round-M-*.png              QA screenshot evidence (MCP captures)
  └── e2e/
      └── batch-N-round-M.md                 e2e verification reports

  Authored e2e tests are Playwright TEST FILES → ui_implementing.e2e.test_dir
  within the project (permanent assets), NOT the workspace.

  QA step list  = the contract between LOOP 2 and LOOP 3:
    produced by QA_TEST (every round, every eval_mode),
    consumed by E2E_AUTHOR. A QA loop never exits toward E2E_AUTHOR without it.


  ═══════════════════════════════════════════════════════════════════════════
  PLAYWRIGHT REQUIRES NO CONFIG OF ITS OWN
  ═══════════════════════════════════════════════════════════════════════════

  The scaffold never invokes Playwright. It only surfaces the URL and the test
  command in its output; the QA sub-agent reaches the Playwright MCP via
  ui_implementing.app.url, and the e2e suite runs through
  ui_implementing.e2e.test_command. No ui_implementing.qa.driver key exists —
  the driver is NAMED in output (so the agent knows to use it), not configured.
