Evaluation Loop

Every phase shares this round-enforcement loop, tuned by eval.min_rounds and eval.max_rounds — both phase-scoped in .forgectl/config. A PASS below the minimum still forces another REFINE cycle; a FAIL at the maximum forces acceptance to prevent infinite loops (force-accept boundary).

eval.min_rounds minimum quality gate eval.max_rounds infinite-loop cap force-accept boundary at max phase-scoped in .forgectl/config
Generic Evaluation Loop
Core Pattern — All Phases
Evaluate → Branch → Enforce
inwork artifact
looprounds++
outACCEPT / REFINE

After any unit of work (Draft, Implement, etc.) the evaluator runs, increments rounds, and produces a verdict. The loop applies two independent constraints: a minimum quality bar that keeps quality high even when the agent passes too early, and a maximum cap that guarantees the batch always terminates.

Loop flow
WORK DONE → EVALUATE → PASS / FAIL → round check → REFINE ⟲ ACCEPT
PASS + rounds >= eval.min → ACCEPT quality satisfied
PASS + rounds < eval.min → REFINE need more eval cycles
FAIL + rounds < eval.max → REFINE fix and retry
FAIL + rounds >= eval.max → ACCEPT forced — cap reached
Decision Matrix
Round Enforcement Rules
Verdict Round Condition Outcome
PASS rounds >= eval.min ACCEPT — quality satisfied
PASS rounds < eval.min REFINE — need more eval cycles
FAIL rounds < eval.max REFINE — fix and retry
FAIL rounds >= eval.max ACCEPT — forced, cap reached
Examples by Configuration
Ex 1 min_rounds = 1 · max_rounds = 3 (typical)
Round 1 EVAL → PASS → ACCEPT done in 1
Round 1 EVAL → FAIL → REFINE
Round 2 EVAL → PASS → ACCEPT fixed
Round 2 EVAL → FAIL → REFINE
Round 3 EVAL → FAIL → ACCEPT forced at max
Ex 2 min_rounds = 2 · max_rounds = 3 (high quality)
Round 1 EVAL → PASS → REFINE below min
Round 2 EVAL → PASS → ACCEPT met min
Round 1 EVAL → FAIL → REFINE
Round 2 EVAL → FAIL → REFINE
Round 3 EVAL → FAIL → ACCEPT forced at max
Ex 3 min_rounds = 1 · max_rounds = 1 (fast pass)
Round 1 EVAL → PASS → ACCEPT
Round 1 EVAL → FAIL → ACCEPT forced, no retry

When min and max are both 1, every outcome terminates immediately — either clean acceptance or a forced-accept with no REFINE cycle.

ui_implementing — Three Loops in Series
Phase 04b — kind: ui
Three Sequential Gates per Batch
loop 1code eval
loop 2qa
loop 3e2e

Each batch passes three sequential gates. Each gate is an independent instance of the generic evaluation loop with its own rounds counter and its own min_rounds / max_rounds budget. An item is "passed" only if all three loops passed within budget; if any loop force-accepted, the item is marked "failed" at COMMIT.

eval_mode Configuration
Three Modes — How Findings are Recorded

Configured per-phase at [specifying.eval], [planning.eval], [implementing.eval], and (one per loop) [ui_implementing.eval], [ui_implementing.qa], [ui_implementing.e2e]. Reconciliation and cross-reference eval inherit specifying.eval's mode.

report (default)
  • Sub-agent writes report to disk
  • forgectl advance requires --eval-report <path>
  • EVALUATE output names report path + prior rounds list
  • REFINE output says: "Study eval file and implement corrections"
direct
  • Sub-agent edits files in place; corrections land as unstaged changes
  • forgectl advance requires only --verdict
  • REFINE output says: "Review unstaged changes (git diff)"
  • No report file written
conversational
  • Verdict communicated verbally by sub-agent
  • forgectl advance requires only --verdict
  • REFINE output says: "Make corrections based on evaluator communication"
  • No report file; no PREVIOUS EVALUATIONS section emitted

All modes: forgectl eval outputs full evaluator context with embedded prompts. --eval-report is accepted but ignored unless mode is report (a warning is printed). Legacy enable_eval_output boolean is honored when eval_mode is unset — true resolves to report, false resolves to conversational.
