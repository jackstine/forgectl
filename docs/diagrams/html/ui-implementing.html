UI Implementing

The UI implementation phase — reuses the implementing spine and inserts two additional verification loops between code eval and commit. Three sequential gates per batch: code eval, QA placement via the Playwright MCP, and end-to-end verification via the Playwright test runner. An item passes only if all three loops pass within their independent round budgets.

Phase 04 (UI) — Batch Loop
Orient + Implement
Role: Senior Software Engineer (UI)
resetseval_round, qa_round, e2e_round → 0
selectsnext batch of unblocked items

Identical to the implementing phase spine: dependency-ordered batches, one item at a time, with full context (steps / files / specs / refs) per item. Every round auto-commits that item when enable_commits: true — first round and every round after an eval FAIL alike (message synthesized from the item's description; --message optional and appended); items move pending → done here. Terminal status (passed / failed) is decided later at the batch-terminal commit boundary (COMMIT, or an inline auto-commit when enable_commits: true) after all three loops complete.

Loop 1 — Code Evaluate
Code Eval Gate
Budget: ui_implementing.eval.min_rounds / max_rounds · counter: eval_round

Shared with the standard implementing phase. An opus sub-agent receives impl-eval.md and batch item details via forgectl eval, checks code against specs, then returns its report via forgectl handoff <report> (report mode) or inline (conv mode). The engineer reviews the Review: line and records a verdict with forgectl advance --verdict PASS|FAIL.

EVALUATE loop
EVALUATE ⟲ IMPLEMENT round 2+ → EVALUATE → QA_TEST (qa_round=1)
FAIL <max → apply eval_mode, fix code → IMPLEMENT (round 2+) → EVALUATE
PASS ≥min → proceed to QA_TEST
FAIL ≥max → force-accept flagged → proceed to QA_TEST
Code EVAL terminates → QA_TEST (step list contract begins)

Loop 2 — QA Placement
QA Gate
Budget: ui_implementing.qa.min_rounds / max_rounds · counter: qa_round
agent1× sub-agent
evalui-qa-eval.md
toolPlaywright MCP
outqa/batch-N-steps.json (required)

The sub-agent receives ui-qa-eval.md, the app launch command, URL, and step-list target path via forgectl eval. It drives the live app through the Playwright MCP: navigates to ui_implementing.app.url, reads the accessibility snapshot to judge placement, exercises controls (click / type / fill / select), reads the console for runtime errors, and captures screenshots as evidence. The QA step list (qa/batch-N-steps.json) is always written — every round, every eval_mode. A QA loop never exits toward E2E_AUTHOR without it. Files are returned via forgectl handoff <qa-report> <step-list>.

QA_TEST loop
QA_TEST ⟲ UI_REFINE → QA_TEST (qa_round++) → E2E_AUTHOR
FAIL <max → UI_REFINE (move, resize, relabel, reorder, rewire — no commit) → QA_TEST
PASS ≥min → step list present → E2E_AUTHOR
FAIL ≥max → qa force-accept flagged → E2E_AUTHOR
UI_REFINE actions
Move elements · Resize · Relabel · Reorder · Rewire controls · No commit

Bridge State — E2E Authoring
E2E Author
Single state — not a loop · consumes QA step list
inqa/batch-N-steps.json (required)
outPlaywright test files → e2e.test_dir
runsui_implementing.e2e.test_command

The engineer reads the QA step list and authors one runnable Playwright test file per scenario into ui_implementing.e2e.test_dir — steps become actions, expected outcomes become assertions. The suite is then run via ui_implementing.e2e.test_command. Pass, fail, or runner error — the engineer advances regardless; the verdict belongs to E2E_VERIFY. Zero scenarios → author nothing, advance directly. Authored test files are permanent project assets, not workspace files.

Flow
Read QA step list → Author Playwright tests → Run e2e.test_command → forgectl advance (e2e_round=1) → E2E_VERIFY
Step list contract satisfied → E2E_VERIFY (loop 3 begins)

Loop 3 — E2E Verification
E2E Gate
Budget: ui_implementing.e2e.min_rounds / max_rounds · counter: e2e_round
agent1× sub-agent
evalui-e2e-eval.md
toolPlaywright test runner
zeroscenarios → PASS (vacuous)

The sub-agent receives ui-e2e-eval.md, the step-list path, test command, and test dir via forgectl eval. It confirms the authored Playwright tests run, pass, and cover the step list. In report mode the sub-agent returns its report via forgectl handoff <e2e-report>. Zero scenarios yields a vacuous PASS. The engineer records the verdict with forgectl advance --verdict PASS|FAIL.

E2E_VERIFY loop
E2E_VERIFY ⟲ E2E_REMEDIATE → E2E_VERIFY (e2e_round++) → COMMIT / inline auto-commit
FAIL <max → E2E_REMEDIATE (fix failing tests or UI under test, re-run suite — no commit) → E2E_VERIFY
PASS ≥min → enable_commits: true: auto-commit batch inline → ORIENT/DONE directly (COMMIT skipped)  ·  enable_commits: false: proceed to COMMIT
FAIL ≥max → e2e force-accept flagged → enable_commits: true: auto-commit batch inline → ORIENT/DONE  ·  enable_commits: false: proceed to COMMIT

Batch Boundary — Terminal Status
Commit
Terminal item status decided here — after all three loops
passedall 3 loops PASSed within budget
failedany loop force-accepted at max_rounds

The only place where items transition to their terminal status. passed = code eval, QA, and E2E all passed within their respective round budgets. failed = any loop reached its max_rounds and was force-accepted. Items stay done while the batch moves through the three loops; status is only finalized at this boundary — the COMMIT state when enable_commits: false, or the inline auto-commit at the terminal E2E_VERIFY transition when enable_commits: true (in which case COMMIT never renders).

Item state progression
pending → done → passed (all three loops PASS in budget)
pending → done → failed (any loop force-accepted at max)
Commit command
enable_commits: true → COMMIT is skipped; the batch already auto-committed inline at the terminal E2E_VERIFY advance (message synthesized from item descriptions)
enable_commits: false → forgectl advance (no git operation)
After commit
more batches / more layers → ORIENT (next batch)
all items complete → DONE
PHASE_SHIFT when all layers complete ui_implementing → planning (next domain) or session complete if queue empty

Two Actors, Three Commands
Engineer (primary agent)
forgectl advance forgectl status
Drives all state transitions. Records verdicts via advance --verdict PASS|FAIL. In report mode: advance --verdict PASS|FAIL --eval-report <path>.
Sub-agent (evaluator — code | qa | e2e)
forgectl eval forgectl handoff
Valid ONLY in the three evaluator states: EVALUATE, QA_TEST, E2E_VERIFY. handoff verifies each file exists, surfaces them on a Review: line, carries NO verdict. Coexists with --eval-report; divergent path warns but does not block.
