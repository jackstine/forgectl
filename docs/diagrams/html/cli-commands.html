CLI Commands

The forgectl command tree — Go binary, Cobra framework; drives a JSON-backed state machine at .forgectl/state/forgectl-state.json. Every phase transition, evaluation verdict, and artifact handoff flows through this interface.

Binary forgectl Framework Cobra State forgectl-state.json init advance status preflight eval handoff add-queue-item set-roots set-commit-hashes generate-workflow
Commands
forgectl init Initialize a new session

Bootstrap a state machine for a given phase. Reads all configuration from .forgectl/config (TOML). Creates .forgectl/state/forgectl-state.json.

Required flags
--from <path> Input file — spec-queue.json, plan-queue.json, or plan.json depending on phase --phase <str> Phase name: specifying · planning · implementing · ui_implementing
Optional flags
--guided Enable guided mode (user checkpoints at each state) --no-guided Disable guided mode
Input by phase
specifying spec-queue.json planning plan-queue.json implementing plan.json ui_implementing plan.json (+ requires ui_implementing.app.* and ui_implementing.e2e.* config, non-empty)
Planning readiness gate (--phase planning only)

init --phase planning is a cold-start entry into a planning cycle, so every domain in the --from plan queue must have an empty <domain-path>/<workspace_dir>/. A dirty workspace fails init with exit 1, names each dirty domain with its path and the workspace close-out remediation, and writes no state file. Ask first with forgectl preflight --from <queue>.

Config (.forgectl/config — TOML)
# Phase-scoped configuration example [specifying] batch = 1 [specifying.eval] min_rounds = 1 max_rounds = 3 [general] enable_commits = false
Example invocations
$ forgectl init --phase specifying --from spec-queue.json $ forgectl init --phase planning --from plan-queue.json --guided $ forgectl init --phase implementing --from plan.json $ forgectl init --phase ui_implementing --from plan.json
output State initialized — .forgectl/state/forgectl-state.json written
forgectl advance Transition to next state

The primary driver. Reads the current state, validates any flags required for that state, and mutates forgectl-state.json. Flags are context-dependent — the valid set changes with the current state.

State-dependent flags
Current state Valid flags
ORIENT (none required)
SELECT (none required)
DRAFT --file <path> override output path (spec only)
EVALUATE --verdict PASS|FAIL   --eval-report <path> (if report mode)   --message optional — appended to the synthesized batch message when the verdict is terminal and enable_commits: true (the batch commits inline on this advance)
REFINE (none required)
ACCEPT --message (planning, if enable_commits)
IMPLEMENT --message optional on every round — appended to the message synthesized from the item's description
COMMIT (none — reached only when enable_commits: false; no git operation occurs)
QA_TEST (ui) --verdict PASS|FAIL   --eval-report <path> (if qa report mode)
UI_REFINE (ui) (none required)
E2E_AUTHOR (ui) (none required)
E2E_VERIFY (ui) --verdict PASS|FAIL   --eval-report <path> (if e2e report mode)   --message optional — same inline batch commit on the terminal verdict
E2E_REMEDIATE (ui) (none required)
RECONCILE (none required)
RECONCILE_EVAL --verdict PASS|FAIL   --eval-report <path>
RECONCILE_REVIEW (none required)
COMPLETE --message (specifying, if enable_commits)
PHASE_SHIFT --from <path> (specifying or gen_plan_q) — both shifts into planning are cold-start entries and are refused by the readiness gate when any incoming domain's workspace is non-empty; the session stays where it is

State transitions (examples)
Evaluate verdict flow
EVALUATE → ACCEPT or REFINE
UI gate verdicts
QA_TEST → E2E_AUTHOR or UI_REFINE
E2E_VERIFY → COMMIT or E2E_REMEDIATE
Phase shift
PHASE_SHIFT → next phase init via --from <path>
Example invocations
$ forgectl advance # ORIENT, SELECT, REFINE, etc. $ forgectl advance --verdict PASS # from EVALUATE $ forgectl advance --verdict FAIL --eval-report report.md # from EVALUATE with report $ forgectl advance --verdict PASS # from QA_TEST or E2E_VERIFY $ forgectl advance --from plan-queue.json # from PHASE_SHIFT $ forgectl advance --message "also drops the legacy shim" # from IMPLEMENT — appended to the synthesized message $ forgectl advance --guided # toggle guided mode on
output Updated state + formatted status showing current position and next action
forgectl status Print current state with action guidance

Human-readable snapshot of the current session. No state mutation. Inherits --dir from the root command.

Flags
(none) No additional flags beyond the root --dir
Example invocations
$ forgectl status
output Human-readable status, next action, overview
forgectl preflight Report planning readiness for a plan queue's domains

Asks the question the planning readiness gate answers at every cold-start entry into planning: does every domain this cycle is about to plan have an empty workspace? A domain is clean when <domain-path>/<workspace_dir>/ is absent, empty, or holds only empty subdirectories. Any regular file at any depth makes it dirty — a leftover plan.json, an eval report, even a lone .gitkeep — as does a directory that cannot be traversed.

Read-only and stateless: it creates no directory, writes no state file, deletes nothing, and writes no log entry. Valid in any state and outside a session entirely — run it before init to learn whether init would be refused. Its verdict is a pure function of the queue's domains and the current filesystem, so it never consults a marker or an "already planned" record.

Optional flags
--from <path> Plan queue JSON to check. Omitted → the active session's pending plan queue (written by generate_planning_queue)
Same evaluation enforced at
init init --phase planning --from <queue> — blocked means exit 1 and no state file phase shift generate_planning_queue → planning — blocked means no transition; the session stays put --from skip specifying → generate_planning_queue with --from, which lands directly in planning ORIENT not gated Intra-session domain boundaries (planning→planning, implementing/ui_implementing→planning). Cold start already cleared them; re-gating would false-block the multi-domain continuation
Example invocations
$ forgectl preflight --from plan-queue.json $ forgectl preflight # uses the session's pending queue
output Planning readiness: READY + inspected count (exit 0), or Planning readiness: BLOCKED + the dirty domains, their workspace paths, and the workspace close-out remediation (exit 1). An unreadable or invalid --from queue, or no queue to resolve, also exits 1.
forgectl eval Output evaluation context for sub-agent

Dumps the full context needed by the AI evaluator sub-agent. Valid in EVALUATE; also QA_TEST and E2E_VERIFY when in ui_implementing. No additional flags.

Valid states
EVALUATE all phases QA_TEST ui_implementing E2E_VERIFY ui_implementing
Output content by state
EVALUATE Items, specs, tests, evaluator prompt QA_TEST Embeds ui-qa-eval.md + app url + step-list path E2E_VERIFY Embeds ui-e2e-eval.md + test command
Example invocations
$ forgectl eval # from EVALUATE — pipe to sub-agent $ forgectl eval # from QA_TEST — includes QA eval prompt + app url $ forgectl eval # from E2E_VERIFY — includes e2e eval prompt + test cmd
output Full context needed by AI evaluator (items, specs, notes, evaluator prompt, phase-specific embeds)
forgectl handoff Register sub-agent artifacts back to the scaffold

The inverse of eval. Used by the sub-agent (AI evaluator) to register generated files back to the scaffold in ui_implementing. Verifies each file exists; surfaces them on a Review: line so the engineer reviews before recording a verdict. Carries no verdict and does not block --eval-report.

Arguments
<file> [<file>…] One or more generated files to register — QA report, QA step list, e2e report
Valid states
EVALUATE QA_TEST E2E_VERIFY same states as eval
Example invocations
$ forgectl handoff qa-report.md $ forgectl handoff qa-report.md qa-steps.json $ forgectl handoff e2e-report.md e2e-tests.spec.ts
output Registered N artifact(s) for review.
forgectl add-queue-item Append a spec to the specifying queue

Appends a new spec entry to the in-flight specifying queue. Domain is resolved from configured domains then session domains; must be supplied via --domain when no match is found.

Required flags
--name <str> Spec name — must be unique --topic <str> Topic of concern --file <path> Path to spec file — must exist; must match <domain>/specs/<name>.md convention
Optional flags
--domain <str> Domain name — required when no match found via auto-resolution
Valid states
DRAFT CROSS_REFERENCE_REVIEW DONE RECONCILE_REVIEW
Example invocations
$ forgectl add-queue-item --name auth-tokens --topic "JWT lifecycle" --file auth/specs/auth-tokens.md $ forgectl add-queue-item --name billing --topic "payment flow" --file billing/specs/billing.md --domain billing
output Added {name} to specifying queue for domain {domain}.
forgectl set-roots Set code search roots for a domain

Writes specifying.domains[<domain>].code_search_roots in the state file. Used to tell the planning and implementing phases where to search for existing code within a given domain.

Required flags
--domain <str> Domain name to configure --roots <str> Comma-separated list of root paths
Example invocations
$ forgectl set-roots --domain auth --roots ./auth,./shared/middleware $ forgectl set-roots --domain billing --roots ./billing,./pkg/payments
output Set code search roots for {domain}.
forgectl set-commit-hashes Set commit hashes for a domain

Overwrites commit_hashes on every completed spec in a domain. These hashes are deduplicated into spec_commits on the plan-queue entry during plan-queue generation. Only valid in CROSS_REFERENCE_REVIEW or DONE within the specifying phase. This is the only way to populate commit hashes when enable_commits is false, or to correct hashes after the fact.

Flags
--domain <str> Domain name. Required at DONE; inferred from the current domain at CROSS_REFERENCE_REVIEW. (positional) One or more commit hashes
Example invocations
$ forgectl set-commit-hashes --domain auth abc1234 def5678 $ forgectl set-commit-hashes abc1234
output Set commit hashes for domain "{domain}": [{hashes}]
forgectl generate-workflow Compile a plan.json into a Claude Code workflow script

Compiles a validated plan.json plus the active .forgectl/config into ONE self-contained Claude Code workflow under .claude/workflows/. The emitted script bakes the plan's items as ordered batches and runs the adversarial evaluation gauntlet — one primary pass per batch, then a bounded mutating-evaluator loop with a git change-detector deciding convergence. It bakes implementing.{batch,implement,eval} and general.enable_commits in at generation time; the script re-reads nothing at run time. The plan and config are read-only. A name collision never overwrites — a prefixed fresh name is chosen and a WARN names both.

Arguments & flags
<plan.json> Path to a produced plan; validated (same rules as forgectl validate) before any file is emitted. -v, --verbose Print DEBUG diagnostics: the resolved config baked into the script and the per-batch item ids in run order.
Example invocations
$ forgectl generate-workflow auth/.forge_workspace/implementation_plan/plan.json $ forgectl generate-workflow plan.json -v
output wrote workflow <path> (slash command: /<domain>-<module>-impl)
forgectl --version Display version
$ forgectl --version v0.0.1
Two-Actor Model
Engineer ↔ Sub-Agent Which actor uses which commands

All commands flow through the same state file. The engineer drives the outer loop; the AI sub-agent receives context via eval and returns artifacts via handoff or advance --verdict.

Engineer · Primary Agent
  • forgectl init
  • forgectl advance
  • forgectl status
  • forgectl preflight
  • forgectl add-queue-item
  • forgectl set-roots
  • forgectl set-commit-hashes
  • forgectl generate-workflow
Writes: Specs · Plans · Code · Notes · Workflows
Sub-Agent · AI Evaluator
  • forgectl eval
  • forgectl handoff (ui_implementing)
Reads: Spec files · Implementation · Notes/refs · Evaluator prompt
Writes: Eval reports · QA reports/steps · e2e tests/reports
