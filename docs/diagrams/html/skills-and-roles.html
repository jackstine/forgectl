Skills & Roles

Each skill defines a specialized AI agent role with specific capabilities, constraints, and workflow knowledge. Skills are loaded via .claude/skills/ symlink and drive every phase of the forgectl pipeline.

Architecture
Skills Architecture

Skills live under skills/ and are symlinked into .claude/skills/ so Claude Code can load them. Commands follow the same pattern via .claude/commands/.

.claude/ ├── commands -> ../commands/ │ └── meta/ │ ├── prompt-structure.md │ ├── gen-prompt-from-discussion.md │ └── start-discussion-to-gen-prompt.md │ └── skills -> ../skills/ ├── planner/ ← Skill 1: Systems Architect (pre-spec) ├── specs/ ← Skill 2: Systems Architect (specifying) ├── implementation_planning/ ← Skill 3: Staff Engineer (planning) ├── implement_from_specs/ ← Skill 5: Senior Engineer (no scaffold) └── implementation/ ← Skill 4: Senior Engineer (implementing)

01 Planner Systems Architect
Phase: Pre-specifying (standalone)  ·  skills/planner/SKILL.md
Purpose
  • Research, discuss, and produce planning documents before specifying begins
  • Does NOT use the forgectl scaffold — standalone workflow
Workspace
.workspace/ ├── SPEC_MANIFEST.md ← Index of all specs (source of truth) ├── planning/ │ ├── <domain>/ │ │ ├── diagrams/ │ │ ├── concepts/ │ │ └── VIEW_MANIFEST.md │ ├── diagrams/ ← Shared diagrams │ └── implementation-planning/ │ ├── implementation-stack.md │ └── implementation-phases.md └── tabled/ ← Deferred plans
Output format
  • # Title
  • ## Topic of Concern
  • ## Context
  • ## Proposal
  • ## Domain
  • ## Depends On
  • ## Open Questions
Constraints
  • Plans are technology-AGNOSTIC
  • Never modifies specs directly
  • Maintains SPEC_MANIFEST.md as source of truth

02 Specs Systems Architect
Phase: Specifying  ·  skills/specs/SKILL.md  ·  uses forgectl scaffold
4 Supported Workflows
  • 1. Generate From Plan (primary — uses forgectl)
    Search → Init → Loop per spec → Reconcile
    ORIENT → SELECT → DRAFT → EVALUATE ⇄ REFINE → ACCEPT
  • 2. Split Existing Spec — uses merge-specs.md methodology; when a spec covers multiple topics of concern
  • 3. Review Spec Corpus — uses cross-specification-review.md; spawns 4–5 parallel sub-agents by concern area; finds contradictions, ambiguities, gaps, stale refs
  • 4. Propagate Design Change — uses cross-cutting-changes.md; when a design decision cascades across multiple specs
Key Principles
  • Topic of Concern: one sentence, no "and"
  • Declarative voice: "the system does…" not "should…"
  • No open questions in specs
  • Technology-aware, not technology-coupled
  • Specs are permanent contracts
Common Eval Findings to Avoid
  • Phantom Observability Entries
  • Unverifiable Invariants
  • Untested Invariants
  • Internal Architecture as Invariants
  • Silent Omissions

03 Implementation Planning Staff Engineer
Phase: Planning  ·  skills/implementation_planning/SKILL.md  ·  uses forgectl scaffold
Purpose
  • Generate validated implementation plans from completed specs
  • Studies specs, existing code, and packages before drafting any plan
Workflow
ORIENT → STUDY_SPECS → STUDY_CODE → STUDY_PACKAGES → REVIEW → DRAFT → VALIDATE → EVALUATE ⇄ REFINE → ACCEPT → PHASE_SHIFT
Produces
<domain>/.forge_workspace/implementation_plan/ ├── plan.json (structured manifest) └── notes/ (per-package implementation guidance) ├── <pkg-a>.md └── <pkg-b>.md

04 Implementation Senior Software Engineer
Phase: Implementing (full scaffold)  ·  skills/implementation/SKILL.md  ·  uses forgectl scaffold
Purpose
  • Execute implementation items with evaluation checkpoints
  • Default code path for kind: code plans
Workflow
ORIENT → IMPLEMENT per item → EVALUATE → COMMIT → DONE
ORIENT (next batch) loops back until queue drains
Tracks progress in
  • {domain}/.workspace/implementation/IMPLEMENTATION_LOG.md
Sub-agent patterns
  • Codebase search — confirm feature doesn't already exist
  • Build/test operations — ONE sub-agent per invocation
  • Evaluation — spawned for forgectl eval
  • Document updates — IMPLEMENTATION_LOG, CLAUDE.md

05 Implement From Specs Senior Software Engineer
Phase: Standalone — does NOT use forgectl  ·  skills/implement_from_specs/SKILL.md
Purpose
  • Quick implementation when specs already exist
  • Bypasses the full planning phase entirely
Workflow (4 steps)
  • 1. Orient — Read specs, check log, study code
  • 2. Implement — Code completely; no stubs
  • 3. Validate — Run tests, diagnose failures
  • 4. Record — Log entry + git commit
Tracks progress in
  • {domain}/.workspace/implement-from-specs/IMPLEMENTATION_LOG.md
References
  • git-commit-guidelines.md
