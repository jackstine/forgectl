================================================================================
                FORGECTL SKILLS & ROLES — Agent Architecture
================================================================================

  Each skill defines a specialized AI agent role with specific capabilities,
  constraints, and workflow knowledge. Skills are loaded via Claude Code's
  .claude/skills/ symlink.

  SKILL 1: PLANNER

  ┌─────────────────────────────────────────────────────────────────────────┐
  │  Role:   Planner (Systems Architect)                                    │
  │  Phase:  Pre-specifying (standalone)                                    │
  │  Uses:   Does NOT use forgectl scaffold                                 │
  │  File:   skills/planner/SKILL.md                                        │
  │                                                                         │
  │  Purpose: Research, discuss, produce planning documents                 │
  │                                                                         │
  │  Workspace:                                                             │
  │  .workspace/                                                            │
  │  ├── SPEC_MANIFEST.md        ◄── Index of all specs (source of truth)  │
  │  ├── planning/                                                          │
  │  │   ├── <domain>/                                                      │
  │  │   │   ├── diagrams/                                                  │
  │  │   │   ├── concepts/                                                  │
  │  │   │   └── VIEW_MANIFEST.md                                          │
  │  │   ├── diagrams/           ◄── Shared diagrams                       │
  │  │   └── implementation-planning/                                       │
  │  │       ├── implementation-stack.md                                    │
  │  │       └── implementation-phases.md                                   │
  │  └── tabled/                 ◄── Deferred plans                        │
  │                                                                         │
  │  Output: Planning documents with:                                       │
  │    # Title                                                              │
  │    ## Topic of Concern                                                  │
  │    ## Context                                                           │

  │  References:                                                            │

  SKILL 2: SPECS
  ═══════════════════════════════════════════════════════════════════════════

  ┌─────────────────────────────────────────────────────────────────────────┐
  │  Role:   Systems Architect (Spectician)                                 │
  │  Phase:  Specifying                                                     │
  │  Uses:   forgectl scaffold (primary workflow)                           │
  │  File:   skills/specs/SKILL.md                                          │
  │                                                                         │
  │  4 Supported Workflows:                                                 │
  │                                                                         │
  │  ┌──────────────────────────────────────────────────────────┐          │
  │  │  1. GENERATE FROM PLAN  (primary — uses forgectl)        │          │
  │  │                                                          │          │
  │  │  Search ──► Init ──► Loop (per spec) ──► Reconcile       │          │
  │  │                       │                                  │          │
  │  │               ORIENT ──► SELECT ──► DRAFT                │          │
  │  │                  ──► EVALUATE ⇄ REFINE ──► ACCEPT        │          │
  │  └──────────────────────────────────────────────────────────┘          │
  │                                                                         │
  │  ┌──────────────────────────────────────────────────────────┐          │
  │  │  2. SPLIT EXISTING SPEC  (reference methodology)         │          │
  │  │                                                          │          │
  │  │  Uses: merge-specs.md methodology                        │          │
  │  │  When: spec covers multiple topics of concern            │          │
  │  └──────────────────────────────────────────────────────────┘          │
  │                                                                         │
  │  ┌──────────────────────────────────────────────────────────┐          │
  │  │  3. REVIEW SPEC CORPUS  (reference methodology)          │          │
  │  │                                                          │          │
  │  │  Uses: cross-specification-review.md methodology         │          │
  │  │  Spawns 4-5 parallel sub-agents by concern area          │          │
  │  │  Finds: contradictions, ambiguities, gaps, stale refs    │          │
  │  └──────────────────────────────────────────────────────────┘          │
  │                                                                         │
  │  ┌──────────────────────────────────────────────────────────┐          │
  │  │  4. PROPAGATE DESIGN CHANGE  (reference methodology)     │          │
  │  │                                                          │          │
  │  │  Uses: cross-cutting-changes.md methodology              │          │
  │  │  When: design decision cascades across multiple specs    │          │
  │  └──────────────────────────────────────────────────────────┘          │
  │                                                                         │
  │  Key Principles:                                                        │
  │    - Topic of Concern: one sentence, no "and"                           │
  │    - Declarative voice: "the system does..." not "should..."            │
  │    - No open questions in specs                                         │
  │    - Technology-aware, not technology-coupled                            │
  │    - Specs are permanent contracts                                      │
  │                                                                         │
  │  Common Eval Findings to Avoid:                                         │
  │    - Phantom Observability Entries                                      │
  │    - Unverifiable Invariants                                            │
  │    - Untested Invariants                                                │
  │    - Internal Architecture as Invariants                                │
  │    - Silent Omissions                                                   │
  │                                                                         │
  │  References:                                                            │
  │    skills/specs/references/                                             │
  │    ├── spec-format.md                                                   │
  │    ├── topic-of-concern.md                                              │
  │    ├── search-specs-for-specifying.md                                   │
  │    ├── merge-specs.md                                                   │
  │    ├── cross-specification-review.md                                    │
  │    ├── cross-cutting-changes.md                                         │
  │    ├── forgectl-state-schema.md                                         │
  │    └── forgectl-state-example.json                                      │
  └─────────────────────────────────────────────────────────────────────────┘

  SKILL 6: UI IMPLEMENTATION
  ═══════════════════════════════════════════════════════════════════════════

  ┌─────────────────────────────────────────────────────────────────────────┐
  │  Role:   Senior Frontend Software Engineer                              │
  │  Phase:  UI Implementing (full scaffold; extends Implementing)          │
  │  Uses:   forgectl scaffold                                              │
  │  File:   skills/ui_implementation/SKILL.md                              │
  │                                                                         │
  │  Purpose: Implement user-facing UI (plan.json kind: ui) and verify it  │
  │           the way a user would, before each batch commits.             │
  │                                                                         │
  │  Workflow (each batch passes three sequential verification loops):     │
  │    ORIENT ──► IMPLEMENT (per item) ──► EVALUATE        ◄ Loop 1: code  │
  │      ──► QA_TEST ⇄ UI_REFINE                           ◄ Loop 2: qa    │
  │      ──► E2E_AUTHOR ──► E2E_VERIFY ⇄ E2E_REMEDIATE     ◄ Loop 3: e2e   │
  │      ──► COMMIT ──► ORIENT (next batch) | DONE                         │
  │                                                                         │
  │  Three evaluator sub-agent roles (all run `forgectl eval`, return      │
  │  artifacts with `forgectl handoff`):                                    │
  │    - Code evaluator  — EVALUATE; same role as the implementing phase.  │
  │    - QA evaluator    — QA_TEST; drives the running app through the      │
  │                        Playwright MCP (navigate/snapshot/click/type/   │
  │                        console), judges placement & controls, and      │
  │                        writes the e2e step list (QA→e2e contract).     │
  │    - E2E evaluator   — E2E_VERIFY; confirms the authored Playwright    │
  │                        tests pass and cover the QA step list.          │
  │                                                                         │
  │  Requires (validated at init): ui_implementing.app.launch_command,     │
  │    .app.url, .e2e.test_command, .e2e.test_dir.                         │
  │                                                                         │
  │  References:                                                            │
  │    skills/ui_implementation/references/                                 │
  │    ├── forgectl-workflow.md                                             │
  │    ├── qa-playwright.md                                                 │
  │    └── subagent-usage.md                                                │
  └─────────────────────────────────────────────────────────────────────────┘
