================================================================================
              EVALUATION LOOP — Round Enforcement Logic
================================================================================

  Every phase uses the same evaluation loop pattern with configurable
  eval.min_rounds and eval.max_rounds (phase-scoped in .forgectl/config)
  to balance quality with progress.

  The ui_implementing phase runs THREE of these loops in series per batch —
  code (eval), QA (qa), and e2e — each with its OWN min_rounds/max_rounds
  budget and its own force-accept boundary. See the dedicated section below.


  ═══════════════════════════════════════════════════════════════════════════
  GENERIC EVALUATION LOOP
  ═══════════════════════════════════════════════════════════════════════════

                          ┌──────────────┐
                          │  WORK DONE   │
                          │  (Draft /    │
                          │   Implement) │
                          └──────┬───────┘
                                 │
                                 ▼
                          ┌──────────────┐
                     ┌───►│  EVALUATE    │◄──────────────────────┐
                     │    │              │                        │
                     │    │  rounds++    │                        │
                     │    └──────┬───────┘                        │
                     │           │                                │
                     │    ┌──────┴──────────────────────┐        │
                     │    │                             │        │
                     │    ▼                             ▼        │
                     │  PASS                          FAIL       │
                     │    │                             │        │
                     │    │                             │        │
                     │    ▼                             ▼        │
                     │  rounds >= eval.min_rounds? rounds >= eval.max_rounds?
                     │    │                             │        │
                     │  ┌─┴──┐                       ┌──┴─┐     │
                     │  │    │                       │    │     │
                     │ YES   NO                    YES   NO     │
                     │  │    │                       │    │     │
                     │  │    ▼                       │    ▼     │
                     │  │  REFINE ───────────────────┼────┘     │
                     │  │  (must meet minimum)       │          │
                     │  │                            │          │
                     │  ▼                            ▼          │
                     │  ACCEPT                    ACCEPT        │
                     │  (quality met)          (forced — prevent│
                     │                          infinite loops) │
                     │                                          │
                     └──────── REFINE ──────────────────────────┘
                          (fix deficiencies)

  REFINE here is the generic "go fix it" step. Which concrete state that is
  depends on the phase and, in the implementation phases, on eval_mode:

    specifying / planning          REFINE
    implementing                   IMPLEMENT (round 2+)   report, conversational
                                   EVALUATE  (self-loop)  direct
    ui_implementing  code loop     IMPLEMENT (round 2+)   report, conversational
                                   EVALUATE  (self-loop)  direct
    ui_implementing  qa loop       UI_REFINE              every eval_mode
    ui_implementing  e2e loop      E2E_REMEDIATE          every eval_mode

  Under eval_mode: direct the evaluator has already corrected the files, so
  there is nothing for an IMPLEMENT round to do — the batch re-enters EVALUATE
  directly and IMPLEMENT runs exactly once per batch. The self-loop carries the
  round increment the IMPLEMENT→EVALUATE transition would otherwise have
  applied, so the counter still climbs toward max_rounds and a repeatedly
  failing batch force-accepts rather than looping forever. The QA and e2e loops
  keep their own refine states in every mode: their evaluators drive a browser
  and a test suite, so there is always non-evaluator work to hand back.


  ═══════════════════════════════════════════════════════════════════════════
  DECISION MATRIX
  ═══════════════════════════════════════════════════════════════════════════

  ┌───────────┬────────────────────────┬────────────────────────────────────┐
  │ Verdict   │ Round Condition        │ Outcome                            │
  ├───────────┼────────────────────────┼────────────────────────────────────┤
  │ PASS      │ rounds >= eval.min     │ ACCEPT  (quality satisfied)        │
  │ PASS      │ rounds <  eval.min     │ REFINE  (need more eval cycles)    │
  │ FAIL      │ rounds <  eval.max     │ REFINE  (fix and retry)            │
  │ FAIL      │ rounds >= eval.max     │ ACCEPT  (forced — cap reached)     │
  └───────────┴────────────────────────┴────────────────────────────────────┘


  ═══════════════════════════════════════════════════════════════════════════
  EXAMPLES BY CONFIGURATION
  ═══════════════════════════════════════════════════════════════════════════

  Example 1: [phase].eval.min_rounds = 1, max_rounds = 3 (typical)
  ───────────────────────────────────────────────────────────────

    Round 1: EVALUATE ──► PASS ──► ACCEPT (done in 1 round)
    Round 1: EVALUATE ──► FAIL ──► REFINE
    Round 2: EVALUATE ──► PASS ──► ACCEPT (fixed in round 2)
    Round 2: EVALUATE ──► FAIL ──► REFINE
    Round 3: EVALUATE ──► FAIL ──► ACCEPT (forced at max)


  Example 2: [phase].eval.min_rounds = 2, max_rounds = 3 (high quality)
  ────────────────────────────────────────────────────────────────────

    Round 1: EVALUATE ──► PASS ──► REFINE (below min, must continue)
    Round 2: EVALUATE ──► PASS ──► ACCEPT (met minimum)
    Round 1: EVALUATE ──► FAIL ──► REFINE
    Round 2: EVALUATE ──► FAIL ──► REFINE
    Round 3: EVALUATE ──► FAIL ──► ACCEPT (forced at max)


  Example 3: [phase].eval.min_rounds = 1, max_rounds = 1 (fast pass)
  ───────────────────────────────────────────────────────────────────

    Round 1: EVALUATE ──► PASS ──► ACCEPT
    Round 1: EVALUATE ──► FAIL ──► ACCEPT (forced, no retry)

  ═══════════════════════════════════════════════════════════════════════════
  UI_IMPLEMENTING — THREE LOOPS IN SERIES  (per batch)
  ═══════════════════════════════════════════════════════════════════════════

  Each batch passes three sequential gates. Each gate is an instance of the
  GENERIC EVALUATION LOOP above, with its own counter and its own budget.

    IMPLEMENT(s) ─► [ LOOP 1: code ] ─► [ LOOP 2: qa ] ─► [ LOOP 3: e2e ] ─► batch
                     eval_round           qa_round          e2e_round      terminal
                     impl-eval.md         ui-qa-eval.md     ui-e2e-eval.md
                     EVALUATE             QA_TEST ⟲         E2E_AUTHOR →
                     (verdict)            UI_REFINE         E2E_VERIFY ⟲ E2E_REMEDIATE

  Budgets (independent, phase-scoped):
    [ui_implementing.eval]  min_rounds / max_rounds   code correctness
    [ui_implementing.qa]    min_rounds / max_rounds   placement & controls
    [ui_implementing.e2e]   min_rounds / max_rounds   end-to-end verification

  ACCEPT vs force-accept work exactly as the DECISION MATRIX above, but PER LOOP:
  a loop terminates on PASS at >= its min, or force-accepts on FAIL at >= its max.
  An item is "passed" only if ALL THREE loops passed within budget; if ANY loop
  force-accepted, the item is "failed". Status is decided at the batch-terminal
  boundary — the COMMIT state when enable_commits: false, or the inline
  auto-commit on the terminal E2E_VERIFY advance when enable_commits: true
  (COMMIT is skipped in that case). The implementing phase's equivalent boundary
  is the terminal EVALUATE advance.

  QA EVALUATION CRITERIA  (ui-qa-eval.md — drives the Playwright MCP)
  ┌────┬──────────────────────┬────────────────────────────────────────────┐
  │  # │ Criterion            │ What the QA sub-agent checks               │
  ├────┼──────────────────────┼────────────────────────────────────────────┤
  │  1 │ Placement            │ Layout/structure via accessibility snapshot│
  │  2 │ Controls             │ Each control click/type/fill/select works  │
  │  3 │ Runtime health       │ Console free of errors while exercising UI │
  │  4 │ Reachability         │ App launches and serves at the given url   │
  │  5 │ Step-list output     │ Emits e2e scenarios (always written)       │
  └────┴──────────────────────┴────────────────────────────────────────────┘

  E2E VERIFICATION CRITERIA  (ui-e2e-eval.md — Playwright test runner)
  ┌────┬──────────────────────┬────────────────────────────────────────────┐
  │  # │ Criterion            │ What the e2e sub-agent checks              │
  ├────┼──────────────────────┼────────────────────────────────────────────┤
  │  1 │ Tests run            │ Authored Playwright tests execute          │
  │  2 │ Tests pass           │ The suite passes via the test command      │
  │  3 │ Coverage             │ Tests cover the QA step-list scenarios     │
  └────┴──────────────────────┴────────────────────────────────────────────┘
  (Zero-scenario step list → E2E_VERIFY verdict PASS, vacuously.)


  ═══════════════════════════════════════════════════════════════════════════
  eval_mode CONFIGURATION
  ═══════════════════════════════════════════════════════════════════════════

  The per-phase eval_mode config flag controls how an eval sub-agent records its
  findings and how the engineer applies them. It has three values.
  Configured at: [specifying.eval], [planning.eval], [implementing.eval],
  and (one per loop) [ui_implementing.eval], [ui_implementing.qa],
  [ui_implementing.e2e].
  (Reconciliation and cross-reference eval inherit specifying.eval's mode.)

  eval_mode: "report"  (default for new sessions)
  ───────────────────────────────────────────────
  - EVALUATE output prints the CONCRETE report path (not a literal <path>): the
    "must write its report to this exact path" line, the advance line carrying
    that same path, and "--eval-report takes this file path, not the report text."
  - forgectl eval emits a "--- REPORT OUTPUT ---" section with the SAME path,
    instructing the sub-agent to create the file there and return only the path
    and verdict; plus a "--- PREVIOUS EVALUATIONS ---" list of prior rounds
  - The path in the EVALUATE action and in eval REPORT OUTPUT are identical
    (computed once by the scaffold) — see specs/eval-report-contract.md
  - REFINE output says: "Study the eval file <path> and implement any corrections"
  - forgectl advance requires --eval-report <path>; if given report prose instead
    of a path, the error hints that a file path is expected
  - Sub-agent writes a report to disk; stored as reference

  eval_mode: "direct"
  ───────────────────
  - EVALUATE output asks the sub-agent to "evaluate and correct" and notes the
    corrections land as unstaged changes (git diff)
  - forgectl eval emits "--- REPORT OUTPUT ---" → "Make corrections directly to
    the <plan|batch|spec> files." and lists prior rounds as "(direct corrections)"
    (reconciliation omits REPORT OUTPUT — it works on staged changes)
  - REFINE output says: "Review unstaged changes from the evaluator (git diff)"
  - forgectl advance requires only --verdict (no --eval-report)
  - No report file; the sub-agent edits the files in place
  - Implementation phases re-enter EVALUATE, not IMPLEMENT. In implementing and
    in ui_implementing's code-eval loop, a FAIL below max_rounds or a PASS below
    min_rounds loops EVALUATE → EVALUATE; IMPLEMENT runs exactly once per batch.
    The self-loop increments the round counter itself, so max_rounds is still
    reached and the force-accept still fires. Specifying and planning are
    unaffected — they continue to route through REFINE — and ui_implementing's
    QA and e2e loops keep UI_REFINE and E2E_REMEDIATE in every mode.

  eval_mode: "conversational"
  ───────────────────────────
  - EVALUATE output includes: "advance with --verdict PASS|FAIL"
  - forgectl eval omits both the REPORT OUTPUT and PREVIOUS EVALUATIONS sections
  - REFINE output says: "Make corrections based off communication with the evaluator"
  - forgectl advance requires only --verdict (no --eval-report)
  - No report file; verdict communicated verbally by the sub-agent

  All modes:
  - forgectl eval outputs full evaluator context (embedded evaluator prompts)
  - --eval-report is accepted but ignored unless mode is "report" (warning printed:
    "--eval-report is ignored, --eval-report is only used in report mode")

  Back-compat (legacy enable_eval_output)
  ───────────────────────────────────────
  eval_mode resolution (EvalModeFor) honors the older enable_eval_output boolean
  when eval_mode is unset. An explicit eval_mode always wins; otherwise:
  - enable_eval_output: true  (per-eval or [general]) → resolves to "report"
  - enable_eval_output: false                          → resolves to "conversational"
